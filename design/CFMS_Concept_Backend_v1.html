Arquitectura de backend — concepto para validar antes de implementar

Hoy todo vive en el localStorage de cada dispositivo (nada se comparte). El backend hace que la configuración, voluntarios, inscripciones, lista de espera y checklists vivan en un lugar central y se sincronicen entre todos los dispositivos — manteniendo el app offline-first (rápido y usable sin red).

Decisión de stack (recomendada)

Google Apps Script (Web App) + Google Sheets como backend — la misma stack del proyecto Gideão 300, que ya dominas y funciona. Coste 0, sin servidor que mantener, y la planilla es legible/editable a mano si hace falta. Login con Google (ya decidido para líderes/admin).

01Las 4 capas

1 · App (PWA en el móvil)
La UI que ya construimos. Lee y escribe siempre primero en el caché local → respuesta instantánea, funcione o no la red.
▲ ▼ sincroniza
2 · Caché local (localStorage / IndexedDB)
Copia local de los datos + una cola de cambios pendientes (lo que aún no llegó al servidor). Es lo que hace el app offline-first.
▲ ▼ HTTPS (pull / push)
3 · API — Apps Script Web App
Un endpoint /exec. GET pull devuelve todo el estado; POST aplica cambios (inscribir, config, checklist…). Valida permisos (Google + allowlist) y reglas (no pasar del cupo).
▲ ▼ lee/escribe
4 · Datos — Google Sheets
Una hoja por entidad (pestañas). La fuente de verdad compartida.

La Config puede guardarse como un JSON en una celda (simple, como ya la tenemos) o desglosada en filas (más “planilla”). Recomiendo empezar con JSON en una celda — migración trivial desde mf_config.

03Cómo sincroniza (offline-first)

Patrón pull + push, el mismo del Gideão 300:

// Al abrir / al reconectar / cada X min:
1. PULL   GET /exec?action=pull&token&idToken
          → { config, voluntarios, inscripciones, checklists }
          → guarda en caché local, refresca la UI

// Al hacer una acción (inscribirse, asignar, editar config…):
2. Escribe YA en el caché local (UI responde al instante) + marca "pendiente"
3. PUSH   POST /exec  { action:'inscribir', activityId, rol, ... }
          → si hay red: aplica en Sheets, confirma
          → si no hay red: queda en la cola; se reintenta al reconectar

Estado de sync (visible en el app)

Un indicador: ✓ sincronizado · ⏳ pendiente (hay cambios sin subir) · ⚠ error · sin conexión. Igual que el Gideão.

04Conflictos y reglas críticas

La mayoría de los datos aquí NO son colaborativos (cada voluntario edita lo suyo), así que los conflictos son raros. Pero hay UN caso crítico:

El cupo de plazas. Dos voluntarios podrían tomar la última plaza a la vez. Solución: la regla de cupo se valida en el servidor (no en el móvil). El servidor, al recibir la inscripción, comprueba el cupo con LockService (bloqueo) y, si ya está lleno, responde “a lista de espera”. El móvil ajusta. Así no hay sobrecupo.
DatoEstrategia de conflicto
Perfil, mis inscripciones, checklist marcadoLast-write-wins por campo (raro chocar; bajo impacto)
Cupo de una plazaValidación en el servidor (LockService) → confirmado o espera
Config (solo Admin la edita)Un solo editor → sin conflicto real

05Seguridad y permisos

  • Login Google (líderes/admin obligatorio; voluntarios teléfono o Google). El servidor valida el idToken.
  • Allowlist en la planilla: quién es admin, quién es líder de qué misión. El servidor comprueba antes de aceptar una escritura sensible (editar config = solo admin; checklist/escala = solo líder de esa misión).
  • Lección del gideao300 (ya en el backlog): en un frontend público el token compartido no es secreto. Aquí la seguridad real es el login Google + allowlist en el servidor. Datos personales de voluntarios viven solo en la planilla (protegida por login), nunca en el repo.

06Plan de implementación (por fases)

  • Fase 1 — Config compartida: subir CONFIG a la pestaña Config; el app hace pull al abrir. (El Admin edita → se guarda en el servidor → todos lo ven.)
  • Fase 2 — Voluntarios + login Google real: perfil en la planilla; allowlist de admin/líderes.
  • Fase 3 — Inscripciones + lista de espera: con validación de cupo en el servidor (LockService).
  • Fase 4 — Checklists: plantilla (en Config) + instancia (pestaña Checklists).
  • Fase 5 — Sync robusto: cola de pendientes, reintentos, indicador de estado, caché offline.

Ventaja

El app ya está construido y probado sobre localStorage. El backend reemplaza la capa de almacenamiento (load/save) por pull/push — la UI, la lógica, las pantallas no cambian. Es una migración de la capa de datos, no una reescritura.
