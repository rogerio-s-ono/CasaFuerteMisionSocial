Arquitectura de datos configurable — documento conceptual (validar el modelo, aún no la UI)

Hoy las cadenas (MercaMadrid, Banco de Alimentos) están fijas en el código. La propuesta: convertirlas en datos de configuración que el Admin crea y edita. Este documento valida el modelo de datos — las entidades, sus campos y cómo se generan las fechas — antes de diseñar la pantalla del Admin.

Cadena Actividad (plantilla) Plaza-rol Rol (catálogo)

01Modelo de entidades

Jerarquía de 4 niveles. Los Roles viven en un catálogo global reutilizable; una Cadena contiene Actividades; cada Actividad tiene Plazas-rol (qué rol y cuántos).

▲ referenciado por ▲

📋 Actividad (plantilla)
id ·id nombre ·{pt,es} hora ·HH:MM duración ·opc. (ej. 12:00–16:00) notas ·{pt,es} opc. recurrencia ·objeto (ver §2) activo ·bool

🎟️ Plaza-rol
rolId → Rol capacidad ·nº de plazas
Clave del diseño: una Actividad es una plantilla (no una fecha). Guardamos la regla de recurrencia, y las fechas concretas del mes se generan bajo demanda — nunca almacenamos una fila por ocurrencia. Es el patrón RRULE (iCalendar/RFC 5545), el estándar de la industria.

02Tipos de recurrencia

Cada actividad define cuándo se repite. Cuatro tipos cubren todas las frentes actuales y futuras:

TipoParámetrosEjemploGenera
semanalweekdayPlaza Mayor · cada martestodos los martes del mes
mensual_posicionweekday, ordinalRecogida · 1er sábado1 fecha/mes (el 1er sábado)
mensual_diaday (1–31)Reparto · día 151 fecha/mes (el día 15)
avulsofechas[]Evento especial · 24 dicsolo las fechas listadas
Ya usamos mensual_posicion hoy (1er sábado / 1ª quarta). Añadir semanal, mensual_dia y avulso hace el modelo general — cubre las otras frentes (Plaza Mayor martes, Villaverde jueves, Cañada Real viernes, Jurídico 1ª miércoles…).

04Cómo se generan las actividades del mes

El motor actual (generateActivities(año, mes)) casi no cambia: en vez de leer un array fijo en el código, lee CONFIG.cadenas. Para cada actividad-plantilla, aplica su recurrencia y produce las ocurrencias datadas — igual que hoy.

// hoy:  generateActivities lee SEED_TEMPLATES (fijo en app.js)
// mañana: generateActivities lee CONFIG.cadenas (editable por Admin)

CONFIG.cadenas
  → por cada actividad-plantilla
      → aplicar recurrencia(año, mes)  // = fechas del mes
      → por cada fecha: crear ocurrencia { fecha, hora, cadena, plazas, roles… }
  → ordenar por fecha+hora  →  agenda del mes (lo que ven voluntarios y líderes)
La inscripción, la vista del líder, la lista de espera y "añadir servidor" no cambian: siguen operando sobre las ocurrencias generadas. Solo cambia de dónde salen las plantillas.

05Decisiones incorporadas (mis recomendaciones)

  • Roles = catálogo global reutilizable; cada cadena elige cuáles usar y con qué capacidad. Evita duplicar "Preparación" en cada cadena.
  • Recurrencia = 4 tipos (semanal, mensual_posicion, mensual_dia, avulso) — cubre todas las frentes.
  • Requisito por rol (ej. "furgoneta") = campo de texto opcional en el catálogo de roles.
  • Líderes por cadena = allowlist de emails en la propia cadena (integra lo que ya diseñamos).
  • Activo/inactivo en cadena y actividad = permite desactivar sin borrar (histórico intacto).
  • i18n (pt/es) en nombres y notas, como ya hace el app.
Para discutir antes de la UI del Admin:
  • ¿La capacidad puede variar por mes/ocasión, o es fija en la plantilla? (hoy propongo fija; el líder ya puede "añadir servidor" para excepciones)
  • ¿Hace falta duración/fin por actividad, o basta la hora de inicio + nota? (Distribución 12:00–16:00 es el único caso hoy)
  • ¿El Admin define el catálogo de roles, o dejamos roles fijos y solo se configuran cadenas/actividades al principio?
  • ¿"Frente" y "Cadena" son lo mismo aquí? (uso "Cadena" como el contenedor configurable; ¿mantenemos ese nombre?)
